# How rk_pki is put together

## The boundary

Seven C symbols, in `rust/include/rk_pki.h`:

```
uint32_t     rk_pki_abi_version(void);
const char  *rk_pki_version(void);
void         rk_pki_string_free(char *);
RkPkiEngine *rk_pki_engine_open(const char *config_json, char **out_error);
void         rk_pki_engine_close(RkPkiEngine *);
char        *rk_pki_call(RkPkiEngine *, const char *op, const char *request_json);
char        *rk_pki_call_stateless(const char *op, const char *request_json);
```

Operations are selected by **name** inside `rk_pki_call`, not by symbol. Two
reasons, both about not breaking a consumer: adding an operation is not a
change of ABI, and the rule that enumerations cross by name applies to the
selector as much as to the values inside it. `rk_pki_abi_version` is what the
Dart side checks before it trusts any other symbol.

## Who frees what

| Value | Allocated by | Freed by |
| --- | --- | --- |
| every `char*` returned | the library | the caller, with `rk_pki_string_free`, exactly once |
| the engine handle | the library | the caller, with `rk_pki_engine_close`, exactly once |
| every `const char*` passed in | the caller | the caller; the library only borrows it for the call |
| `rk_pki_version()` | static storage | nobody |

Nothing else crosses, so there is nothing else to leak. On the Dart side each
returned string is read and freed on the same line (`RkPkiLibrary.takeString`),
and the handle is released by `RkPki.close()`. A `NativeFinalizer` on
`rk_pki_engine_close` is attached as a net for a caller who forgot; it is
guaranteed to run but never at a moment anyone can name, which is why it is not
the mechanism.

## Nothing escapes as a panic

Every entry point runs its body inside `catch_unwind` and turns a caught panic
into `{"ok":false,"error":{"kind":"nativeFault",...}}`. A panic unwinding out
of `extern "C"` is undefined behaviour, and this is the worst place for it: the
decision being made is whether a machine may be talked to, and the till has to
keep selling either way. The crate pins `panic = "unwind"` in its release
profile for the same reason — `abort` would make the guard a lie.

## Where the private key is

It is generated by `rcgen` inside the native library, written to the store, read
back into a `Zeroizing<String>` for the operation that needs it, and dropped.
No function above `identity`/`ca` returns it, no operation name maps to it, and
no exported symbol has a shape that could carry it. On the Dart side the store
handle lives inside a worker isolate; the pointer is not sendable, so it cannot
reach the interface isolate even by accident.

A test in `tests/trust_and_expiry.rs` calls every operation and asserts that no
answer contains a private-key PEM header — the rule as an assertion rather than
as a comment.

## Isolates

`RkPki` owns one long-lived worker isolate that holds the open store for its
whole life. Not `Isolate.run` per call: that would spawn an isolate each time
and reopen the store with it, and the point of the worker is that the key stays
in one place. Secret hashing is the exception — it needs no store, so it runs
on a short-lived isolate per call, which is the right shape for something
called at login and never in a loop.

## Modules

| module | what it decides |
| --- | --- |
| `ffi` | the boundary: catch, borrow, hand over, free |
| `engine` | operation names, request shapes, the response envelope |
| `ca` | the installation's root, invites, and what a certificate is allowed to say |
| `identity` | this machine's key, its signing request, installing and reading its certificate |
| `verify` | judging somebody else's certificate, through `rustls-webpki` |
| `store` | files, permissions, invites and revocations on disk |
| `model` | the identity URN, and reading a certificate back into public facts |
| `profile` | the two profiles and the one rotation rule |
| `secret` | Argon2id |
| `pem` | PEM to DER, through `rustls-pki-types` |

## The identity a certificate carries

```
CN  = machineId
O   = installationId
OU  = machineKind          (till, shopServer, chainServer, clusterNode, relayClient)
SAN = URI  urn:telepos:v1:installation:<inst>:machine:<id>:kind:<kind>:profile:<profile>
      DNS  <names the caller asked for>
      IP   <addresses the caller asked for>
```

Names and addresses are two lists, not one, and that is a correctness matter
rather than a tidiness one: a TLS client matching `https://192.168.1.50/`
consults `iPAddress` entries and nothing else, so a certificate carrying that
address as a `DNS` name fails the handshake while reading, to a human, exactly
like one that should work. Neither list is guessed when omitted — this library
sees one interface list and the machine may be on several networks, so an
absent address list means "no addresses", never "work it out".

Every component is a name. Identifiers are restricted to
`[A-Za-z0-9._-]` so the URN parses back unambiguously — a colon inside a
machine id would make it lie. Rights are not in here and never will be: a
change of rights must not require a reissue.

## What the authority decides, and what the request decides

The request contributes one thing that is trusted: the public key, whose
possession it proves by signing itself. The authority decides subject,
alternative names, key usage, extended key usage, basic constraints, serial and
validity. `rcgen`'s `CertificateSigningRequestParams::signed_by` would sign the
requester's own parameters — `is_ca` included — so this crate does not use it
and builds its own `CertificateParams` around the requested key instead.

## Time

Every operation accepts an optional `nowUnix`. That makes expiry and rotation
testable without waiting a month, and it is also what the health screen needs
in order to report a clock that has drifted. It is not a security hole: Dart
and the native library are the same process with the same privileges, and the
real boundary is the authority's signature, not the clock.

## What is not here

No ACME, no OCSP responder, no HSM or platform key holder, and no subject
outside the till / server / relay-client model. Revocation is a local list of
fingerprints, so there is no CRL distribution either: a short lifetime is the
passive mechanism and that list is the active one.

The per-platform build wiring *is* here, and was not always. Up to 0.1.0 the
crate was a plain `cdylib`/`staticlib` behind a C ABI with nothing to carry it
into a Flutter build; 0.2.0 made the package a Flutter FFI plugin, one
mechanism for the whole family of `rk_*` packages. There is still no
`hook/build.dart`, and there must not be — see
[`native-build.md`](native-build.md).
